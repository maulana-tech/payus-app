# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Payus is a payments app: users get a @username, payment links, invoices and a merchant checkout API, paid through PayPal and recorded in a double-entry ledger. All twelve seats on the landing page are built: six are deterministic code on the money path, six call a model and only ever propose or draft. `README.md` lists what works and what does not; `docs/plan.md` is the dated work plan and the decisions already locked in; `docs/setup.md` is local setup, `docs/api.md` the widget and checkout API.

When adding a payment rail, put the integration behind the existing modules (invoices, paymentLinks, developer/checkouts) rather than threading a provider SDK through the UI.

## Commands

pnpm workspace (only `web`), Node 22+, pnpm 10. `pnpm` may not be on PATH — `corepack pnpm …` works.

```sh
pnpm install
pnpm dev                                  # Next.js on :3000
pnpm --filter web test                    # vitest run (also test:watch, test:coverage)
pnpm --filter web exec vitest run test/money.test.ts       # single test file
pnpm --filter web exec vitest run -t "name"                # single test by name
pnpm --filter web exec tsc --noEmit       # typecheck
pnpm --filter web biome:check             # biome lint+format check (biome:fix to apply)
pnpm --filter web build                   # standalone output in .next
pnpm --filter web build:local             # non-standalone build in .next-local (start:local to run)
pnpm --filter web db:migrate              # applies web/drizzle/*.sql to DATABASE_URL (reads .env.local)
pnpm --filter web db:generate             # regenerates a migration after editing schema.ts
```

`pnpm build` needs a syntactically valid `NEXT_PUBLIC_PRIVY_APP_ID` (25 chars): the Privy provider refuses to initialize without one and prerendering fails. `migrate:up` must run before the first boot — it creates the collections and indexes. Biome is the linter/formatter of record; `pnpm lint` (`next lint` + `.eslintrc.json`) is secondary. `web/scripts/webhook-receiver.mjs` is a local sink for testing webhooks.

## Architecture

### Session and keys (client)
- `web/src/components/SessionProvider.tsx` owns the session: Privy login → passkey (PRF) or PIN unlock → account master in a ref → username claim and account type. `useSession()` is what every screen consumes. Masters and derived keys stay in page memory; never send them to the server or persist them unencrypted.
- `web/src/lib/`: `passkey.ts` (PRF) and `keys.ts` (PIN escrow, Argon2id) produce the master; `derive.ts` HKDFs it into the signing seed, the messaging secret and a local-vault key; `signing.ts` (Ed25519) and `usernameClaim.ts` sign and verify the `@username → keys` claim; `sealedBox.ts` is anonymous X25519→AES-GCM for payloads the server only stores as ciphertext (payment requests); `crypto.ts`, `ids.ts` (base62 public ids), `invoicePdf.ts`, `paymentLinks.ts`, `csv.ts`, `auth-routes.ts`, `brand.ts`.
- `lib/brand.ts` holds `APP_NAME` and `KEY_NS`. `KEY_NS` feeds key derivation: changing it after launch makes every existing key and ciphertext unreadable.

### Domain logic (`web/src/features/`)
Framework-free modules shared by routes, components and the server: `invoices` (`money.ts` minor-unit parsing/formatting, `input.ts` zod schemas + totals, `recurrence.ts`, `types.ts`), `developer/signature.ts` (webhook HMAC, `Payus-Signature: t=…,v1=…`), `embed` (`bridge.ts`, `snippet.ts`), `account/accountType.ts` (which nav items each account type shows), `notifications`, `recovery`, `pwa`. Prefer adding logic here, and unit-testing it, over inside components or routers.

### Routes (`web/src/app/`)
`(dashboard)/` is the signed-in group: dashboard (`OverviewScreen`), links, invoices, requests, developers and settings — each page is a thin wrapper around `DashboardGuard` (sign-in redirect, loading skeleton, "claim a username first") plus one screen from `components/dashboard/screens/`. `DashboardPlaceholder` is the shape a page keeps while there is no username yet; `settings` uses it. `(canvas)/` is the second signed-in group: one route, `/canvas/[id]` (`id` is a shop's id, or `new`), with a layout that keeps the dashboard's colours and drops everything else — no navigation, no page header (`DashboardGuard header={false}`), no dithered backdrop (`DashboardBackground backdrop={false}`). Public: `/pay/[username]` and `/pay/[username]/[slug]` (`components/pay/PayPanel.tsx`), `/i/[token]` (`components/invoices/InvoicePanel.tsx`, served `no-referrer` + `noindex`), `/privacy`, `/unsubscribe/[token]`, and `/embed/*` — the only framable routes, driven by `public/embed.js` (no build step, no dependencies; keep it that way). API: `api/trpc/[trpc]`, `api/v1/checkouts` (REST, API-key auth), `api/payments/paypal/orders` + `.../orders/[orderId]/capture` (public, the invoice token is the capability), `api/webhooks/paypal` (PayPal-verified), `api/cron/invoices` and `api/cron/outbox` (both `Authorization: Bearer $CRON_SECRET`; only the first is in `web/vercel.json`).

### Server
- tRPC `appRouter` in `src/server/root.ts`; modules in `src/server/modules/<name>/` split into `*.router.ts` (maps domain errors → `TRPCError`), `*.service.ts`, `*.schema.ts`, `*.errors.ts`. Modules: `accounts` (PIN escrow, passkey record, account type), `profiles` (signed @username claims, verified with `lib/usernameClaim.ts`), `paymentLinks`, `invoices` (one-off + recurring, reminders, `reportPayment`), `requests` (sealed ciphertext), `developer` (API keys, webhooks, checkouts), `notifications`, `ledger` (double-entry postings), `payments` (PayPal orders, captures, `applyInvoicePayment`), `outbox` (queued work + its handlers). Shared infra in `src/server/lib/` (`privy.ts`, `email.ts` via Resend, `rateLimit.ts`, `paypal.ts`, `cronAuth.ts`) and `src/server/db/` (`schema.ts` for the tables, `client.ts` for the pooled Drizzle instance and `isUniqueViolation`).
- `protectedProcedure` requires a verified Privy access token (Bearer header or `privy-token` cookie, see `context.ts`). Privy is login only (embedded wallets off).
- Money is stored as integer minor units in strings (`amountMinor`, `totalMinor`, `paidMinor`) with an ISO 4217 `currency`; `features/invoices/money.ts` is the only place that parses or formats it. No floats.
- Env: public vars in `src/env.ts` (`NEXT_PUBLIC_PRIVY_APP_ID`), server-only in `src/env.server.ts` (`DATABASE_URL`, `CRON_SECRET`, `PRIVY_*`, `RESEND_API_KEY`, `EMAIL_FROM`, `APP_URL`, `PAYPAL_ENV`, `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `PAYPAL_WEBHOOK_ID`). Add new vars to the zod schema and `web/.env.example`. `next.config.mjs` also loads a repo-root `.env` before Next starts.
- Postgres via Drizzle: edit `src/server/db/schema.ts`, then `pnpm db:generate` (writes SQL to `web/drizzle/`) and `pnpm db:migrate`. Money columns are `numeric(20, 0)` minor units, which the driver returns as strings — the services and the API pass those strings around and only `features/invoices/money.ts` parses them.
- Claiming one row for a job (recurring invoices, reminders) goes through `claimOne` in `invoices.service.ts`: `SELECT … FOR UPDATE SKIP LOCKED` inside a transaction, so a cron run and a dashboard visit cannot claim the same invoice.
- `isUniqueViolation` walks the `cause` chain: Drizzle wraps driver errors, so the pg code `23505` is not on the error it hands you.
- Auth routing: `web/src/middleware.ts` + `src/lib/auth-routes.ts` gate the dashboard routes on Privy cookies. Adding a dashboard route means adding it to `auth-routes.ts`, `navItems.ts`, `features/account/accountType.ts` **and the literal `matcher` in `middleware.ts`** — Next needs a literal there, so `test/middleware.test.ts` is what keeps the two lists in step.
- Headers in `next.config.mjs`: everything refuses framing except `/embed/*`; `/i/*` is `no-referrer` + `noindex`. (The COOP/COEP cross-origin isolation the WASM wallet needed is gone — don't reintroduce it without a reason.)

### The agents
**Bedrock's structured-output schema is a subset of JSON Schema.** Measured against `au.anthropic.claude-sonnet-4-6`: `enum`, `pattern`, `maxLength` and `type: ["string","null"]` are accepted, while **array `minItems`/`maxItems` and numeric `minimum`/`maximum` are rejected with a 400**. Keep those bounds in the zod schema — which is what decides whether an answer is acted on anyway — and say the range in the property's `description` so the model still knows it.

`server/lib/claude.ts` is the only place a model is called: `askForJson()` sets the model (`claude-opus-5-5`, thinking always on so the parameter is omitted), the effort, and **structured outputs** (`output_config.format`) — not forced tool use, which that model rejects with a 400. Without `ANTHROPIC_API_KEY` the agents are off and say so; the rail is unaffected.
`server/modules/agents/` holds one file per seat — `payer`, `allocator`, `builder`, `reporter`, `collector`, `advisor` — and they are all the same shape:
- **The agent holds no limits of its own.** It proposes; the Guardian decides. A second copy of the limits here would be a second, drifting source of truth.
- **Facts come from the ledger**, assembled by `payerFacts()` and spelled out by `payerPrompt()`. The model is never asked to remember a balance.
- **The destination must be one we showed it.** That is a check after parsing, not a line in the prompt — an address the model invented never reaches the Guardian.
- **The shape is validated twice**: the API constrains it, then zod decides whether this application will act on it. A schema the API honoured is not the same as an answer worth executing.
- `ask` is injectable, so `test/payerAgent.test.ts` runs the whole decision path on every commit without spending anything. That file is the agent's eval set; add cases to it rather than trusting the prompt.
- The model id and prompt version land on the proposal and in the audit log, so a decision can be traced to what produced it.
- **The Reporter may not state a figure it was not given.** `reporterFacts()` builds the set of permitted figures; `unknownNumbers()` scans the answer and any number outside that set throws the report away — including a correct subtraction, because working one out is the thing this seat must not do. Single digits in prose are allowed; everything else has to have been handed over.
- **The Collector does not decide whether to write.** `stopReason()` is pure and is the whole of "knows when to stop": settled, nothing outstanding, no address, not overdue, asked inside the last `QUIET_DAYS`, or already asked `MAX_ASKS` times. The model is only reached once that returns null, so the limit cannot be talked out of. The draft is then held to the Reporter's check (the pay link is stripped first, since a URL carries digits that are not claims about money) and must contain that link. It never sends: `agents.sendChase` is the owner's action, and the count that `stopReason` reads goes up there.
- **The Advisor does not write the query.** It chooses one of the six in `QUESTIONS` by name — an `enum` in the schema, then a lookup in a `Map`, so nothing it said is ever interpolated anywhere — and we run it scoped to the owner. The rows come back to the answer step as the only figures it may use, and to the screen under the answer, because an answer whose rows you cannot see is a claim. It has no write path of any kind.
- `thinking: {type: "adaptive"}` is sent explicitly, because it is not the default everywhere: Opus 5.5 always thinks and ignores it, Sonnet 4.6 does not think at all without it.
- Each has an eval file (`test/*Agent.test.ts`, and `test/storefront.test.ts` for the Builder) that drives the whole decision path against a stubbed model. Add a case there rather than trusting the prompt.

### Storefronts
A storefront is **configuration plus one sanitised block of prose**. `features/storefront/config.ts` holds the one schema; the hand editor (`screens/StorefrontScreen.tsx`) and the Builder agent are both held to it, and `components/storefront/StorefrontPanel.tsx` is the only renderer. Every ordinary field — title, blurb, item names — still reaches the page as text; `test/storefrontRender.test.tsx` is the test behind that claim, so do not introduce `dangerouslySetInnerHTML` for one.
- **The one HTML field goes through `storefront/sanitize.ts`, and nothing else.** `sanitizeShopHtml()` is called inside the service's `html()` helper, so no write path — agent, editor, seed — can store markup that skipped it: an allowlist of text, list, table, `a`, `img` and `div`/`span` tags, no `style` attribute, `https`/`mailto` links only, classes limited to `shop-*`, links forced to `rel="noopener noreferrer nofollow ugc"`, and `MAX_HTML` (8000) characters. It returns `removed`, which the editor shows, so an author learns what the policy took out instead of wondering. Both columns are stored: `html_raw` is what they wrote, `html_clean` is what renders.
- **`shop-` classes are a short vocabulary, not a stylesheet.** The sanitiser keeps classes matching `/^shop-[a-z-]{1,24}$/` and `ShopHtml` styles exactly five of them (`shop-lead`, `shop-muted`, `shop-center`, `shop-cols`, `shop-card`). The canvas toolbar inserts them. Adding a shape means adding a rule there, not loosening the allowlist.
- **Two layers behind that allowlist.** `ShopHtml` renders `htmlClean` inside an `<iframe sandbox="allow-same-origin" srcDoc=…>` with **no** `allow-scripts`, so even a hole in the sanitiser has no script to run; and `publishedStorefront()` strips `html` from the public view (`PublicStorefrontView`), so the unsanitised draft never leaves the server. The editor previews through `storefront.previewHtml` rather than rendering locally — there is one sanitiser and it is the server's. `test/sanitizeShopHtml.test.ts` holds the policy down.
- **Everything a payer sends is checked against the stored item, not trusted.** `startStorefrontOrder` reads the item fresh and enforces: sold out refuses; a count is held to that item's own `limit` (and `MAX_QUANTITY`) whatever the request says; a count on an item not sold by the number is ignored, not honoured; a payer-named amount must sit inside the shop's `minMinor`/`maxMinor`; and `MAX_ORDER_MINOR` caps any single order however it is reached, including price × quantity. The browser-side checks in `StorefrontPanel` exist only so the button does not invite a refusal — they are not the guard. `startLinkOrder` carries the same cap.
- **A shop chooses a look, it does not describe one.** `features/storefront/theme.ts` holds four layouts, three themes and six accents; `paletteVars()` turns a choice into CSS variables and the renderer carries no colours of its own. That is the answer to "can it be prettier": make the template better and widen the vocabulary. Free markup is the one exception, and it is fenced as above — do not widen the fence to earn a layout; add a field. A storefront page is also outside `AppShell`'s chrome, because it is the merchant's page and not ours.
- **The editor is a page, not a dialog.** `/canvas/[id]` is the whole window: the controls on the left (Page, Items, HTML, Look) and the shop's actual page on the right, at a phone's, a tablet's or the full width. The thing on the right is `StorefrontPage` — the same component the public is served, given the draft — so there is no second renderer to keep in step and no sketch that can flatter the real page. `features/storefront/draft.ts` owns the three conversions between a stored shop, the mutation's input and that preview; `components/canvas/` holds the screen, the lazily-loaded CodeMirror editor (`HtmlEditor`, no other route pays for it) and the toolbar's snippets. The old `EditorDialog` is gone — do not bring a second editor back.
- **A new shop opens on five starters, not on a blank page.** `features/storefront/starters.ts` holds them as complete drafts — layout, palette, items priced the way that kind of shop prices things, and a block of prose. While the owner is choosing, the canvas renders the starter being considered through the same `StorefrontPage`, so a starter is judged as the page it would become. Picking one only fills the editor; there is no "made from a template" state afterwards. `test/storefrontCanvas.test.tsx` parses every starter through `storefrontInput`: a starting point the schema refuses is a trap, since the owner would meet the error on their first save.
- **The shop page measures itself, not the window.** `Shell` in `StorefrontPanel.tsx` is a `@container` and its breakpoints are `@min-[640px]:`, so the canvas can show the page at 414px and have it answer the way a phone would. A `sm:` added in there would silently lie in the preview.
- **The agent writes a draft; the owner publishes.** Putting a price in front of the public is a commercial decision, so it is not the model's. That is also why publishing needs no Guardian proposal kind.
- Reserved and duplicate addresses are refused **by the schema**, not by a check inside the agent — a duplicate check there was written, found to be unreachable, and deleted. Put a rule where both writers pass through it.
- `oddPrices()` compares against the median of what this merchant has charged before and **points**, rather than refusing: the owner is the one publishing.
- Buying an item writes an invoice first (`startStorefrontOrder`), so a shop sale settles down the same path as everything else. The browser may send only *which* item, never a price.
- The public page is client-fetched like `/i/[token]` and `/pay/*`, so it has no server-rendered content; all three are `noindex`.

### The Guardian
Nothing moves money without a proposal, and no proposal is decided by a model. `features/guardian/decide.ts` is a pure function — proposal + policy + context → `allow | ask | refuse` with a reason per rule — and `server/modules/guardian/` writes the proposal, records the decision, holds consent and runs it. The owner's own "Release" button goes through it, so the road the agents will take is already the one in daily use.
- **Consent is bound to a hash.** `proposalHash(kind, payload)` is sha256 over `canonical()` (keys sorted at every depth). `approvals` is a **log**, one row per act of consent, each naming the hash it was given for; `execute()` compares the newest approval's hash with the proposal's current hash and refuses on a mismatch (`approval.void` in the audit log). Amending a proposal moves the hash and puts it back to `awaiting`.
- **A refusal is a record, not an error to swallow.** A refused proposal is written with its findings before `ProposalRefusedError` is thrown.
- **Every rule is evaluated**, not just the first to fire, so the audit says everything that was wrong; the verdict is the harshest finding and `reason` quotes only the decisive ones.
- `intentKey` rides in the payload and so into the hash: submitting the same attempt twice finds the first proposal instead of writing a second. The proposal id then becomes the payout's `intentKey`, which is why an approved proposal can only ever pay once.
- `executeApproved()` is the door an executor knocks on, and the only place the hash check can catch a race.
- **Proposal kinds are a union.** `decide()` dispatches on `proposal.kind` (`payout`, `split.change`) and `execute()` dispatches the same way; adding a third kind means a `*Findings` function and an `apply*` function, nothing else. Rules that only the Guardian can see — a *total* share across rules, a daily total across payments — belong here; a per-item bound belongs in the agent's own schema, and the Allocator has both for exactly that reason.
- The Guardian guards **agents**, not the owner: `ledger.createRule` lets a person set any split by hand. That is deliberate — the owner is the authority the limits exist to serve.
- Proposals left unanswered are closed by `expireStaleProposals()`, called from `/api/cron/outbox`.

### The embed widget
`public/embed.js` (no build step, no dependencies — keep it that way) frames `/embed/*` and documents the events it dispatches. Those events come from `features/embed/bridge.ts`, mounted by `components/embed/EmbedBridge.tsx` on every embed page: without it the iframe never resizes and `payus:paid` never fires, which is how it sat for a while. A panel rendered with `embed` posts `payus:paid` itself when a payment lands.

### The money path
A payment is four steps, and only the last two may change what anyone is owed:
1. **Order** — `POST /api/payments/paypal/orders` with an invoice token creates a PayPal order for what is still due and a `payments` row (`order_id` unique).
2. **Capture** — either the payer's browser calls `.../capture`, or PayPal's `PAYMENT.CAPTURE.COMPLETED` webhook arrives. Both converge on `recordCapture()`.
3. **Posting** — `recordCapture` posts the capture to the ledger (cash and the PSP fee in, the gross into `in_flight:<owner>`), marks the payment captured, and calls `applyInvoicePayment`, which is also what the dashboard's "mark as paid" uses. The merchant webhook, the owner's notification and the client's receipt fire once, on the transition to `paid`.
4. **Settlement** — `settleCapture()` divides `in_flight` by the owner's `split_rules` and credits each target. It runs inline for speed and, if that throws, is queued on `ledger.settle.capture` so money cannot sit in `in_flight` unnoticed. Releasing what is left goes through `releasePayout()`.

Going back the other way is a fifth step, `recordRefund()` — reached from the owner's **Refund** button (`startRefund`) or from PayPal's `PAYMENT.CAPTURE.REFUNDED` webhook, and safe to run twice from either.

Rules that hold this together, and that a change must keep:
- **The ledger is the idempotency key.** `ledger.post(txn, postings)` refuses Σdebit ≠ Σcredit before touching the database and inserts a `ledger_txns` row whose id is deterministic (`capture:<captureId>`), so a replay returns `{ posted: false }` and writes nothing. `trialBalance()` must stay `0n`.
- **Account ids are derived, never typed.** Use the `account.*` helpers in `modules/ledger/accounts.ts`; the id (`<kind>`, `<kind>:<owner>`, `pos:<owner>:<slug>`) is what tells the ledger an account's kind and normal side. `balance()` reports in that normal direction, so assets and liabilities both read positive; `rawBalance()` is debit − credit.
- **A webhook body is a hint, not a number.** The route verifies the delivery with PayPal, stores it under its `event_id` (primary key ⇒ a redelivery is a no-op) and queues outbox work in the same transaction; the worker reads the capture back from PayPal for the amounts.
- **The invoice is reported with a sum, not a delta.** `capturedTotal()` adds up the captured `payments` rows, so re-running a job cannot double-count.
- Outbox jobs are claimed with `FOR UPDATE SKIP LOCKED`, retried with a growing delay, and parked as `failed` after 8 attempts. Due-ness is compared against the database clock (`now()`), not a JS `Date` — `available_at` has microsecond precision.
- **The split engine is pure.** `features/split/evaluate.ts` takes an amount and rules and returns allocations; it touches nothing. Percentages are of the whole amount (not the running remainder), the percentage group is settled with largest-remainder so no cent is lost or invented, a rule that asks for more than is left gets what is left, and the remainder is the owner's. The invariant every test checks first: Σ allocations === the amount in. `split.service.ts` reads the rules and resolves a target (`tax_reserve`, `platform_fee`, `merchant_payable`, `pos:<slug>`) to a ledger account.
- **A payout cannot be sent twice.** `sender_batch_id` is `sha256(owner|amount|currency|destination|intentKey)`, where `intentKey` identifies the *attempt* — a nonce the release dialog holds while it is open, and later the id of a Guardian-approved proposal. PayPal replays its batch for a repeated id, and the ledger transaction `payout:<batch>` refuses a second posting. Deriving it from ledger position does **not** work: the payout's own posting moves the position, so a retry would read as a new intent (this was tried and reverted).
- **A refund comes out of the pots the capture went into.** `features/refunds/reverse.ts` is pure and has the arithmetic: the shares are read back from the *settlement's own ledger entries* (not recomputed from today's rules, which may have changed), and each step is the difference between two whole-amount allocations — so three refunds of a third add up to the capture exactly instead of drifting a cent per rounding. The policy decision behind it: tax set aside on a sale that was undone is not tax. A rolling reserve was the alternative and was not taken, because it withholds money from every merchant to pay for something rare. `merchant_payable` may go negative, and that is the honest reading when the money was already paid out.
- **A refund cannot be made twice.** Three locks, because there are three ways to arrive: `refunds.refund_id` is PayPal's id (unique), `refunds (payment_id, intent_key)` is unique so a retried attempt returns its own refund instead of asking PayPal again, and the posting `refund:<refundId>` can only land once. `startRefund` checks the attempt **before** the amount left, since the first try has already reduced it. Only a `COMPLETED` refund posts; a pending one is recorded and waits for the webhook.
- **A refunded invoice is owed again.** `reportPayment` takes the absolute figure, so refunds report `capturedTotal − refundedForInvoice` and the invoice falls back to `pending`. `becamePaid` stays false, so no second receipt is sent.
- **An unsent payout posts nothing.** If PayPal refuses, the `payouts` row is marked `failed` with the reason and the ledger is untouched, because no money left. Without `PAYPAL_PAYOUTS_ENABLED=true` the release is deliberately recorded as `payout.simulated` and labelled as such in the UI — never as a real payout.

### Approvals on Telegram
Optional, and off without `TELEGRAM_BOT_TOKEN`. A chat proves itself with a single-use code (`/start <code>`) — the chat id is never taken from a message body as authority, only looked up — and `ownerForChat()` is the whole of what a chat may act for. The buttons call the same `approveProposal` / `refuseProposal` as the dashboard, so the hash check, the expiry and the audit trail are identical; only `via` differs. The webhook verifies `X-Telegram-Bot-Api-Secret-Token` and always answers 2xx once it has handled an update, because Telegram retries anything else and a retried decision is not wanted. Asking the chat is a side effect of a proposal becoming `awaiting` (`waitingFor()`), never awaited and never allowed to throw: a bot being down must not stop a proposal being recorded.

### Reports
`features/reports/settlement.ts` is pure and owns the arithmetic; `modules/ledger/reports.service.ts` only fetches the period's entries. The screen (`SettlementPanel`), the CSV and the PDF (`lib/settlementPdf.ts`) all render the one report object, so none of them can drift from the others. The line that earns the feature is the reconciliation: the `paypal_cash` account's own movement is compared against what taken − fees − refunds − payouts says it should have been, and when they differ the difference is **shown**, because a posting the report has no category for is exactly what you want to hear about. A simulated payout is counted separately from a real one everywhere it appears.

### Deployment
`Dockerfile` (three stages) + `render.yaml` (web service, Postgres, two cron containers) + `docker-entrypoint.sh`. The runtime stage carries the Next **standalone** bundle only: because `outputFileTracingRoot` is the repository, that bundle lands as `/app/node_modules` + `/app/web/server.js`.

Two consequences that have already bitten once, so do not undo them:
- **`scripts/migrate.mjs` uses `pg` and nothing else.** drizzle-orm's migrator is *not* in the traced bundle — the app imports the query builder, not the migrator — so a script that used it worked locally and died in the container. Ours keeps drizzle's own bookkeeping exactly (`drizzle.__drizzle_migrations`, one row per file, keyed by the sha256 of the file's contents, the journal's timestamp), and `test/migrations.test.ts` migrates a database with *drizzle's* migrator and then asks ours what is left to do. The answer has to be nothing.
- **`NEXT_PUBLIC_*` is build-time.** Next inlines it, so the two public ids are `ARG`s in the Dockerfile. A build with a bogus `NEXT_PUBLIC_PRIVY_APP_ID` fails while prerendering `/`, because the provider calls Privy during the export — the fix is a real id, not making pages dynamic.

### The SDK (`packages/js`)
`@payus/js` is dependency-free and uses `fetch` + Web Crypto, so it runs on Node 18+, Bun, Deno and the edge runtimes. Built with `pnpm build:sdk` from the repo root. `web/test/sdk.test.ts` verifies a signature made by the server's own `signWebhook` — a client library that agrees only with itself is how this goes wrong, so the test imports both sides. `constructEvent` throws instead of returning null on purpose, and `getCheckout` encodes the id rather than pasting it into a URL.

### Tests (`web/test`)
Vitest, flat files in `web/test/` (not colocated), `node` environment by default; component tests declare `// @vitest-environment happy-dom` and mount through `test/renderWithTRPC.tsx`. `server-only` is stubbed (`test/stubs/`); `@` aliases `web/src`. Service tests that need a real database use `test/helpers/pgTestDb.ts`: it creates a throwaway database, runs the migrations into it, and skips the whole file when no local Postgres is reachable (`PAYUS_TEST_DATABASE_URL`, default `postgres://localhost:5432/postgres`) — six files do, including `ledger.test.ts` and `moneyPath.test.ts`, so run the suite with a Postgres up or those guarantees go unchecked. `moneyPath.test.ts` stubs only `server/lib/paypal.ts`; verification, the ledger, idempotency and the invoice logic all run for real.

### Dashboard screens
`components/dashboard/screens/` holds one screen per page plus `kit.tsx` (Panel, Ledger/Cell, Stat, Money, StatusChip, CopyButton, ListRow, RowMenu/RowMenuItem, EmptyState, ErrorNote).
- **A row shows one primary control and a `RowMenu`.** Four or five pills of equal weight made the destructive one — an unlabelled bin between two words — the hardest thing on the row to notice, and gave every row a different width, which moved the amount beside it. More than one secondary action goes in the menu, where it gets a sentence ("Ask the Collector to chase", "Void INV-001"). Requests is the one list with two visible buttons, because it only ever has two and both are decisions.
- **A list reserves its actions column.** `<Ledger style={{ "--row-actions": "12.5rem" }}>` fixes the width `ListRow` gives its controls, so every amount in that list stops at the same place. `test/dashboardWidth.test.tsx` holds this, and the rule under it: **a cell may never widen the ledger**. Grid and flex items default to `min-width: auto` — their min-content width — and `truncate` is `white-space: nowrap`, whose min-content width is the *whole untruncated string*. One long meta line once measured 574px, pushed the track to 616px on a 390px phone, and `overflow-x-clip` cut 226px off the right of every panel on the screen. `.dash-ledger > * { min-width: 0 }` in `globals.css` is what stops it, wherever a call site wraps a cell.
- **Small labels stay at 70% ink or darker**, and nothing dims a container *and* its text (two 60% labels inside a 70% row measured 3:1). Checked with `agent-browser a11y` at 390px as well as desktop: the mobile tab bar only exists at the narrow width, and its labels were failing there alone.

`TransactionsScreen` is the one grid: **AG Grid** (community, `AllCommunityModule`) over `ledger.entries`, themed with `themeQuartz.withParams` pointed at the `--dash-*` variables so it follows the mode — which it learns from `useDashMode()` (reads `data-dash-mode` through a MutationObserver, unlike `useDashboardMode()` which owns the toggle's state). Its footer sums both columns; they must agree. The look is set by `components/dashboard/styles.ts` and the `--dash-*` tokens: pills for controls, sharp hairline cells for data, and **no hue** — status is shown by weight (filled ink = settled, hairline = open, faded = closed). The one exception is `--dash-err`, because a failure has to read as a failure. Screens read through `trpc.*` and invalidate `ledger.summary` whenever money moves.

### The landing (`components/landing/editorial/`)
A separate language from the app: ink field (`ed-dark-2`), hairline frame, full-bleed painted loops in `public/landing/`, oversized Cormorant serif, mono micro-labels. `agents.ts` is the twelve-seat table the pinned `council.tsx` pans across — a seat's `status` (`live` | `building`) is a factual claim about the repository, so change it only when the code changes. Films: `split` (hero and closing), `arrive` (the rail), `together` (the agents), `council` (the table).

### UI
Tailwind v4 (`@tailwindcss/postcss`), shadcn-style primitives in `web/src/components/ui/` (incl. `glass.ts`), Base UI, lucide icons, GSAP/Motion, sonner toasts. Dashboard chrome: `AppShell` → `DashboardBackground` → `DashboardShell` (nav, mode toggle, account menu) with `DashboardPageHeader`, `DashboardNotice`, `styles.ts`. Landing uses `components/landing/` primitives (`Chrome`, `Nebula`, `DitherField`, `ScrollReveal`); the long narrative sections of the old product were deleted, `Hero.tsx` is a short replacement. `.agents/skills/` holds vendored UI skills (`ui-taste`, `ios-design`, symlinked from `.kiro/skills/`).
